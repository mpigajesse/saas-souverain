## 1. Verdict

**NON TENU — à refaire après réparation de la pile.** Le portail n'était pas
servi pendant la mesure : **100 % des requêtes ont échoué** (connexion rompue).
La cible L-01 (200 req/s soutenus, 0 × 5xx, p95 < 200 ms) ne peut pas être
évaluée tant que la pile PME n'est pas saine. La cause racine est interne à la
pile (etcd sans quorum → pas de primaire PostgreSQL → HAProxy sans backend →
`ss-node` ne joint pas la base), **pas** une faiblesse de charge du portail.

Le harnais (`load/l01_portail.js`) et la méthode sont validés par un **contrôle
positif** (k6 contre un service sain : 0 % d'échec, p95 13,75 ms). La
correction consiste à réparer la pile puis à **relancer le même script**,
sans le modifier.

## 4. État de la pile pendant la mesure (cause racine)

Sondes au moment de la mesure :

```
ss-node:9001  -> connexion acceptée puis « connection reset by peer » (000)
amane-etcd    -> unhealthy : "failed to commit proposal: context deadline exceeded"
Patroni :8008 -> vide (aucun primaire élu)
amane-haproxy -> backend « primaire » sans serveur sain (aucun `server` actif)
amane-application (listmonk) -> Restarting (1), redémarrage n° 5377, « error connecting to DB: EOF »
ss-node logs  -> « PostgreSQL : injoignable — expected to read 5 bytes, got 0 bytes at EOF »
```

Chaîne de défaillance : **etcd sans quorum** → Patroni ne promeut aucun
primaire → HAProxy n'a plus de backend → `ss-node` ne joint pas PostgreSQL →
son écouteur HTTP réinitialise chaque connexion → l'application hébergée
crash-loope (DB EOF). Le portail est donc **indisponible** pour une cause
d'infrastructure, indépendante de toute charge.

`docs/tests/captures/l01-portail-indispo.png`.*

## 5. Méthodologie

- **Script** : `load/l01_portail.js` (k6), paramétrable via `BASE_URL`.
- **Profil** : mixte **80 % lecture / 20 % écriture** (tirage `Math.random()<0.8`).
- **Paliers** : `ramping-arrival-rate`, **20 → 50 → 100 req/s**, **2 min par
  palier** (6 min au total), `preAllocatedVUs=100`, `maxVUs=300`.
- **Seuils** : `http_req_failed < 1 %` et `p(95) < 200 ms` sur la **lecture**
  (trend `lecture_latence` par nature de requête).
- **Sortie** : `load/results/l01.txt` (en-tête + journal complet + agrégats).

Commande exacte :

```bash
BASE_URL=http://127.0.0.1:9001 K6_NO_USAGE_REPORT=true \
  ~/.local/bin/k6 run load/l01_portail.js
```

### Contrôle positif de l'outil (indépendant du portail)

Pour prouver que k6 et les seuils fonctionnent, un run court (10 s, 5 req/s)
contre un service **sain** du banc (`pgadmin` `:5050`) :

```
http_reqs......: 102   10.18/s
http_req_failed: 0.00%  0 out of 102
http_req_duration p(95): 13.75 ms
```

→ l'outil et la méthode sont bons ; l'échec L-01 vient bien de la cible.

- Débit réel servi : **0 req/s** (les 43,33 req/s sont des tentatives, pas des
  succès).

## 8. Conclusion et correction

**Conclusion : NON TENU.** Le portail PME est indisponible (panne etcd →
Patroni → HAProxy → base), donc aucune des cibles de charge L-01 n'est
mesurable en l'état. Ce n'est pas un résultat de performance mais un
**défaut de disponibilité** de la pile, antérieur à la mesure.

**Correction avant reprise :**
1. Rétablir le quorum etcd (3 membres / témoin) et l'élection d'un primaire
   Patroni ; vérifier `http://127.0.0.1:8008/cluster` non vide.
2. Vérifier que HAProxy a un backend sain et que `ss-node` joint PostgreSQL
   (plus de « got 0 bytes at EOF » dans `docker logs ss-node`).
3. Laisser `amane-application` démarrer ( DB joignable ) et `ss-node` servir
   `/amane/`.
4. **Relancer le même `load/l01_portail.js` sans modification** ( BASE_URL ) et
   comparer aux cibles du §7.

**Réserves.** Activité hôte parasite continue (piles de test `a06-*`/`a09-*`,
VM QEMU) sans effet sur le réseau `amane` du banc PME ; aucune commande de ce
worker n'a touché aux conteneurs `amane-*` (aucun `docker rm`/`down`/`stop`).
La pile était déjà dégradée avant la mesure (documenté dans `docs/STATE.md`).
